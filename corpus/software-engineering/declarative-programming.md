# Declarative Programming

**TL;DR**: Declarative code models the *flow* of an application (what happens) rather than listing atomic steps (how). Functional programming makes this concrete: functions are first-class, behavior is composition of transformations on data, not methods on objects. Point-free / tacit style composes functions directly without naming intermediate values.

## Imperative vs declarative

| | Imperative | Declarative |
|---|---|---|
| Core unit | Statement ("do this, then that") | Expression / transformation |
| Origin | Assembly/C; mirrors hardware | ML (1970s), Haskell, Scala; SQL |
| Strength | Easy to reason about at small scale | Scales better to large problem domains |
| Example | For-loop iterating and mutating state | `.map().filter().reduce()` pipeline |

"When looking at large-scale problems, many tiny instructions start to turn into noise."[^src] At small scope, imperative is fine and often clearer. At application scale, declarative code "should flow like prose — tell a clear story."[^src]

## Functional programming

"Functional" refers to *functions* as the unit of work, not "whether it works."[^src]

OOP recipe: Have a thing → have the thing do something to itself (methods on objects).
Functional recipe: **Do stuff** (functions transform data).[^src]

Key difference: OOP drives toward class hierarchies and inheritance to manage state; functional code focuses on "having data" and transforming it. When functions are first-class citizens, behaviors are easier to express and, arguably, understand.[^src]

Python has partial functional support (map, filter, reduce, list comprehensions, closures). TypeScript/JavaScript support it ergonomically with arrow functions and chaining.

## Point-free (tacit) style

Compose a series of functions into a wrapping function without naming intermediate values. Named after "pointing" (referring to arguments) — point-free code doesn't name the arguments.

Example (TypeScript — baking a cake):[^src]

```typescript
// Standard (with intermediate variable names):
function bakeCake(ingredients: Ingredient[], oven: Oven): Cake {
    const preparedIngredients = prepare(ingredients);
    const preheatedOven = preheat(175.0, oven);
    const cookedFood = cook(preparedIngredients, preheatedOven);
    return cookedFood as Cake;
}

// Point-free / composed:
const bakeCake = (ingredients, oven) => cook(
    prepare(ingredients),
    preheat(175.0, oven)
) as Cake;
```

The function signature `(Ingredient[], Oven) → Cake` communicates intent even without knowing the function name.[^src]

## Lazy evaluation

Related concept: deferring work until results are actually needed (YAGNI applied to computation). Polars lazy mode and Spark transformations are practical examples: operations are collected into a query plan and optimized before any computation runs. See also[^src] for context — the source explicitly connects declarative pipelines (Spark SDP framework) to the same ideas.

## Connection to data engineering

SQL is the original declarative grammar for data. Spark's DataFrame API, Polars lazy mode, and pipeline frameworks like dbt are all declarative in structure: you describe *what* the output should look like, not *how* to compute it step by step.
